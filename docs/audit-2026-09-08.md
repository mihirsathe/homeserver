## New since 2026-09-01 (found 2026-09-08)

### P1

- [ ] **Nextcloud breaks on every array start.** `emhttpd` runs `chmod 0777` + `chown nobody:users`
      on every share root at array start (syslog 17:36:06: `shcmd (74)`/`(75)` on `/mnt/user/nextcloud`).
      Nextcloud's `datadirectory` *is* that share root, so `status.php` returns 503 ("data directory is
      readable by other people"), `occ` refuses to run, the container is unhealthy, and `verify-stack.sh`
      fails 4 checks. It cannot self-heal: the dir is owned by uid 99, so www-data's `chmod 0770` gets
      EPERM (`nextcloud.log`: `chmod(): Operation not permitted at OC_Util.php#486`, every 30 s).
      This never showed before because the box had not rebooted since 2026-08-29. Fix options, best
      first: (a) move the data dir one level down (`/mnt/user/nextcloud/data`, owned 33:33, 0770) and
      update `config.php` + the compose bind; (b) `'check_data_directory_permissions' => false` in
      `config.php` (weaker — the files stay world-readable on the host). Then rerun `verify-stack.sh`.

- [ ] **Nextcloud user files are on the cache pool, not the array.** The `nextcloud` share is
      `shareUseCache="no"` but all 67 MB live at `/mnt/cache/nextcloud`; there is no
      `/mnt/disk*/nextcloud`. The mover never touches a cache=no share, so this is stranded on the
      SSD pool with no parity, while any *new* write would land on the array — a split share. Docs
      and CLAUDE.md call this "array-direct". Fix: flip to cache=yes, run the mover once, flip back
      to no; then `verify-stack.sh` should assert the files are on `/mnt/user0`.

- [ ] **PR #36 (SAB 6G) is merged but not deployed.** The deployed checkout
      (`/mnt/user/appdata/homeserver`, branch `master`) sits at `cd6004e`, 4 commits behind
      `origin/master`; the running `sabnzbd` container still has a 2 GiB ceiling against a 4G article
      cache — the exact OOM condition the PR fixes. `docker compose up -d --dry-run` with master's
      compose recreates only `sabnzbd`, nothing else. Deploy: `git pull --ff-only` in the main
      checkout, then `docker compose --env-file .env.docker up -d sabnzbd`.

- [ ] **Lidarr is running again.** The 2026-09-01 manual stop was undone by the reboot
      (`media_stack_up` runs `compose up -d` and Lidarr is still declared). It stays that way until
      PR #39 merges and is deployed.

### Memory ceilings after the RAM upgrade (proposal, not applied)

Current limits are `deploy.resources.limits.memory` on master; usage is the idle snapshot on
2026-09-08 right after boot. Ceilings are hard limits, not reservations, so the sum can exceed
physical RAM — but with 187 GiB there is no reason to run anything tight.

| Service | Now | Idle use | Proposed | Why |
|---|---|---|---|---|
| plex | 8G | 137 MiB | 16G | concurrent transcodes + scans; also move `/transcode` to tmpfs (`/dev/shm` is 94G) to spare the SSD |
| sabnzbd | 6G (2G deployed) | 80 MiB | 12G | raise `cache_limit` 4G → 8G in `configs/sabnzbd/sabnzbd.ini`; par2/unrar headroom stays 4G |
| ollama | 8G | 650 MiB | 32G | mmap of every pulled model + CPU spill when the 6 GB GPU is contested; makes `OLLAMA_CONTEXT_LENGTH` 16384 (the claudecoach ask) affordable on the RAM side |
| coach (chess) | 6G | 61 MiB | 8G | room to raise `CHESS_COACH_ENGINE_HASH_MB` 4096 → 8192; lc0 itself is VRAM-bound |
| nextcloud | 2G | 127 MiB | 4G | PHP workers at `memory_limit=512M` each |
| nextcloud-db | 1G | 46 MiB | 4G | then `shared_buffers` 128MB → 1GB, `effective_cache_size` → 3GB |
| nextcloud-redis | 256M | 19 MiB | 512M | file-locking cache grows with files |
| radarr / sonarr / lidarr | 1G each | ~140 MiB | 2G each | import/scan bursts; lidarr only until #39 lands |
| bazarr | 1G | 218 MiB | 2G | subtitle sync spikes |
| seerr | 512M | 216 MiB (42 %) | 1G | closest to its ceiling at idle |
| profilarr | 256M | 80 MiB (31 %) | 512M | same |
| tautulli | 512M | 82 MiB | 1G | history DB grows |
| gluetun, prowlarr, actual_server, actual-ai, nextcloud-cron | 256M–768M | < 30 % | keep | nowhere near |
| claudecoach (own compose) | **none** | 92 MiB | 4G | only container on the box with no ceiling |

Proposed sum ≈ 93 GiB of 187, leaving ~90 GiB for page cache, FUSE, and Unraid itself.
